## Records

### docs/decisions.md
Record every decision you make that the specification does not determine.

Record a decision when:
- the specification is silent on something you had to decide;
- the specification is ambiguous and you chose one interpretation;
- two parts of the specification seem to conflict and you chose how to resolve it;
- you chose a library, framework, data structure, or algorithm that changes externally observable behavior
  (responses, status codes, timing, ordering, concurrency, persistence).

Do not record purely internal choices that do not change observable behavior (class names, package layout, formatting).

Write each entry when you make the decision, not afterwards. Append only: do not rewrite or delete earlier entries.
If you change a decision later, add a new entry that names the entry it replaces.

Use this format for each entry:

```markdown
## D-001: <short title>
- Date: YYYY-MM-DD
- Spec reference: <section number(s)>
- What was undetermined: <quote the relevant spec text, or say what is missing>
- Decision: <what you decided>
- Alternatives considered: <other options>
- Reason: <why you chose this one>
- Affected files: <paths>
- Tests covering it: <test names, or "none">
- Replaces: <D-xxx, or "none">
```

### docs/completion-report.md
Write this report once, after every task in `tasks.md` is finished.
Writing the report is the last step: do not change code or tests while writing it.
If you notice a problem while writing, do not fix it; list it in section 7.

Use these sections, in this order:

1. **Summary**
   Overall status (complete or partial) and a short paragraph describing what was built.

2. **How to build, run, and test**
   The exact commands to build, start every service, and run the tests,
   plus the versions of the main tools and runtimes used.

3. **Implemented features**
   A table with one row per specification section:
   `Spec section | What it requires (one line) | Status (implemented / partial / not implemented) | Implementation location (files)`

4. **Test results**
   The exact test command(s) you ran, when you ran them, and the results as reported by the tool:
   passed, failed, and skipped counts per module, and the names of any failed or skipped tests.
   Copy the numbers from the tool output; do not round or summarize them.

5. **Specification-to-test mapping**
   For every specification section, list the tests that check it (`file::test name`).
   If no test checks a section, write "none" for that section. Do not leave sections out.

6. **Decisions**
   A list of the entries in `docs/decisions.md` (ID and title).

7. **Known limitations and deviations**
   Anything not implemented, implemented differently from the specification, known bugs,
   and problems you noticed while writing this report.

8. **Least confident areas**
   The parts of the implementation or the tests you are least confident about, and why.
